EndlessRunner · Code Walkthrough

The half-wired chain

Six defects from this codebase, each shown as the code that shipped and the code that fixes it. They are ordered by how far you have to look to see the problem — from one wrong line, to one wrong assumption about which system owns what.

How to read this

Every "before" block is real code from the template, not an invented example, and every fix here has been applied to the codebase. To see the "before" state, check out a commit from before the event-architecture review.

Try covering the "after" block and finding the bug first. In all six cases the defect is visible without running the game — which is the point. These are bugs you can read.

1

The event nobody publishes Applied

SlideController.cs · SlideArcController.cs

A slide has three stages: SlideRequested (asked for) → SlideStarting (validated, begin) → SlideStarted (animating). Three files describe how it works. All three disagree.

BeforeSlideController.cs
/// Does NOT publish events - validation pass-through allows
/// auto-chain to fire SlideStarting.
///    Publishes: (none - auto-flow handles event progression)

    // Event auto-chains will handle SlideRequested -> SlideStarting
    _isSliding = true;
    _lastSlideTime = Time.time;

    TempleRunBus.Publish(TempleRunEvents.SlideStarted, this, null);
BeforeTempleRunAutoEventFlow.cs
//{ TempleRunEvents.SlideRequested, TempleRunEvents.SlideStarting },
// SlideStarting -> SlideStarted: Published by SlideController

Three contradictions in one mechanic. The comment says it publishes nothing — it publishes. It says the auto-chain fires SlideStarting — that mapping is commented out. And SlideArcController, whose own docs claim it subscribes to SlideStarting, actually subscribed to SlideStarted and published nothing.

Net result: SlideStarting was a dead event. Declared, documented, never published, never heard.

AfterSlideController.cs
///    Publishes: TempleRunEvents.SlideStarting (only once validation passes)

    _isSliding = true;
    _lastSlideTime = Time.time;

    // Published here rather than auto-chained from SlideRequested:
    // SlideRequested is the bridge's raw translation of the input, so an
    // auto-chain would fire even when the checks above reject the request.
    TempleRunBus.Publish(TempleRunEvents.SlideStarting, this, null);
The rule

A doc comment is a claim, not evidence. Trace the chain: for every event, find who publishes it and who subscribes. An event with a publisher and no subscriber is an extension point; one with a subscriber and no publisher is a bug.

2

The gate that was never closed Applied

DashController.cs · TempleRunAutoEventFlow.cs

Dash has a cooldown. DashController exists to enforce it. Read carefully and work out what actually stops a dash from happening.

BeforeDashController.cs
/// Does NOT publish events - validation pass-through allows
/// auto-chain to fire DashStarting.

private void OnDashRequested(string eventName, object sender, object data)
{
    if (_isDashing) return;

    var dashConfig = Blackboard.Instance.DashConfig;
    if (dashConfig == null) { ...; return; }

    float timeSinceLastDash = Time.time - _lastDashTime;
    if (timeSinceLastDash < dashConfig.DashCooldown)
        return;                          // <- "rejects" the dash

    _isDashing = true;
    _lastDashTime = Time.time;
}                                          // publishes nothing
BeforeTempleRunAutoEventFlow.cs
{ TempleRunEvents.DashRequested, TempleRunEvents.DashStarting },

Every return in that method is decorative. The auto-chain fires DashStarting from DashRequested — the event that arrives before any of this runs. DashSpeedController listens for DashStarting and dashes. The cooldown never prevented a single dash; it only kept bookkeeping.

Slide had the same shape, which is why that mapping was commented out — someone hit the problem, disabled the chain, and left the controller half-converted.

AfterDashController.cs
    _isDashing = true;
    _lastDashTime = Time.time;

    // Published here rather than auto-chained from DashRequested, which is
    // the bridge's raw translation of the input: the old chain fired even
    // when the checks above rejected the request.
    TempleRunBus.Publish(TempleRunEvents.DashStarting, this, null);
The rule

An auto-chain runs before any validation. So a *Requested event that arrives raw from input can never be chained to *Starting — the controller that validates must publish *Starting itself. Chain the stages nothing guards; publish the stage a gate protects.

3

Head or tail, four lines apart Applied

PlayerFailedController.cs

One coroutine. It freezes the player after a stumble, waits, then unfreezes. Both halves go through the same three-stage chain — Requested → ing → ed. Only one half does it correctly.

BeforePlayerFailedController.cs
private IEnumerator DeathDelay()
{
    TempleRunBus.Publish(TempleRunEvents.PlayerPaused, this, Time.time);
    //                                    ^ the TAIL of the chain

    yield return new WaitForSecondsRealtime(TempleRunConstants.ResumeDelay);
    _pauseCoroutine = null;

    TempleRunBus.Publish(TempleRunEvents.PlayerResumeRequested, this, Time.time);
    //                                    ^ the HEAD of the chain
}

Publishing the tail directly skips the middle rung. PlayerPausing never fires, so a fade, a SFX duck, or a HUD dim has no event to attach to — while the resume half, four lines below, enters at the head and runs the full chain.

This is a migration that stopped halfway. The same defect existed at two other sites, and a fourth still does: ShieldEffect publishes ObstacleRecovered directly, skipping both recovery rungs.

AfterPlayerFailedController.cs
    // Enter the chain at its head and let the auto-flow run
    // PlayerPauseRequested -> PlayerPausing -> PlayerPaused.
    TempleRunBus.Publish(TempleRunEvents.PlayerPauseRequested, this, Time.time);
The rule

Publish at the head and let the chain run. Publishing a terminal state directly reaches the same endpoint while quietly deleting every intermediate — and the intermediates are where presentation attaches.

4

Subscribing to the cause, not the state Applied

Metronome.cs · TurnCollisionDetector.cs · DistanceController.cs · SegmentAdvanceTrigger.cs · SetMusicPlayer.cs

Five unrelated systems each need to shut down when a run ends. Each wrote the same line. Look at the handler names.

Beforefive separate files
TempleRunBus.Subscribe(TempleRunEvents.PlayerDied, StopMetronome);
TempleRunBus.Subscribe(TempleRunEvents.PlayerDied, OnGameEnding);
TempleRunBus.Subscribe(TempleRunEvents.PlayerDied, OnGameOver);
TempleRunBus.Subscribe(TempleRunEvents.PlayerDied, OnGameEnding);
TempleRunBus.Subscribe(TempleRunEvents.PlayerDied, OnPlayerDied);  <- the honest one

Four of the five handlers are named for the state — the run ended — while subscribing to a particular cause of it. That works exactly as long as dying is the only way a run ends.

The fifth is more interesting. SetMusicPlayer.OnPlayerDied is named honestly — and it was the last one found, precisely because the name matched the event. But read what it does:

private void OnPlayerDied(string eventName, object sender, object data)
{
    _musicPlayer.Stop();          // stopping the run's music
}

Stopping the run's music is a run-ended behavior, not a death-specific one. The honest name concealed the same bug. The test is not whether the handler's name matches the event — it is whether the handler's behavior matches it.

It isn't. Quitting reaches the same state by another road:

UserQuitRequested → TempleRunEndRequested → TempleRunEnding → TempleRunEnded
                                             PlayerDied never fires

So on quit the music and metronome keep playing, distance keeps accumulating, and turn-failure detection stays armed — five systems still running a run that ended.

Afterfive separate files
TempleRunBus.Subscribe(TempleRunEvents.TempleRunEnded, StopMetronome);

// and the honest one gets an honest name to match its new event:
TempleRunBus.Subscribe(TempleRunEvents.TempleRunEnded, OnRunEnded);

Note what the fix is not. You cannot auto-chain PlayerDied to anything new: it is already a key in the dispatch dictionary, and that dictionary is Dictionary<T,T> — one successor per event. The ceiling forces a subscriber move rather than a mapping.

The rule

Subscribe to the state you actually mean. If your handler is named for a state, the event should be too — otherwise you have silently assumed that one cause is the only cause, and the second route in will not announce itself.

5

Borrowing the neighbour's vocabulary Applied

PlayerFailedController.cs · PauseController.cs

A stumble freezes the player for about a second. There was no "freeze" event, so it was written using the pause events. Two concerns now share one state machine — and one boolean.

BeforePauseController.cs
private bool _isPaused = false;

// set from an event this class neither owns nor initiated
TempleRunBus.Subscribe(TempleRunEvents.PlayerPaused, OnPause);

public void TogglePauseResume()
{
    if (_isPaused)
        TempleRunBus.Publish(TempleRunEvents.PlayerResumeRequested, ...);
    else
        TempleRunBus.Publish(TempleRunEvents.PlayerPauseRequested, ...);
}

The failure hitch publishes PlayerPauseRequested, which reaches PlayerPaused, which sets _isPaused = true in a controller that did not ask for it. Now press pause during the stumble:

obstacle hit  → PlayerPauseRequested → … → PlayerPaused
                                            ↳ _isPaused = true

player presses pause → TogglePauseResume() sees true → PlayerResumeRequested

Pressing pause un-pauses the game. Two independent writers, one boolean. And because DeathDelay() waits in real time, its own resume fires afterward regardless of what the player did.

The fix is not a cleverer flag. It is that a gameplay hitch and a user pause are different concepts and need different events. The enum has held the right ones all along:

AfterTempleRunEvents.cs — already present, never published
PlayerFailRequested = 0,
PlayerFailing       = 1,
PlayerFailed        = 2,
AfterTempleRunAutoEventFlow.cs
{ TempleRunEvents.PlayerFailingAtTurn,     TempleRunEvents.PlayerFailing },
{ TempleRunEvents.PlayerFailingAtObstacle, TempleRunEvents.PlayerFailing },

Two keys may share one value, and both slots are free. Those two lines give failure its own vocabulary, revive a subscription in DistanceController that had never once run, and collapse three controllers that each subscribed to both specifics into one event apiece.

PlayerFailedController now owns only the length of the hitch — it releases with PlayerFailed — and PlayerLifeController no longer has to publish a resume to cancel a pause a different controller started.

But wiring it exposes a second problem, and this is the part worth dwelling on. Once a hitch and a user pause can both freeze the game, a single boolean is wrong — whichever ends first thaws the other. The freeze has to track who is holding it:

AfterGameTime.cs
/// Freezes are tracked as a SET, not a bool: a user pause and a post-failure
/// hitch can overlap, and with a single latch whichever one ended first would
/// thaw the other. Membership also makes a repeated hold or a duplicate
/// release harmless.
private enum FreezeReason { UserPause, Failure }

private readonly HashSet<FreezeReason> _freezes = new HashSet<FreezeReason>();

private void Apply()
{
    _timeScale = _freezes.Count > 0 ? 0f : 1f;
}

A set rather than a counter, so a duplicate release cannot drive the count negative and silently unfreeze the game — the classic refcount bug, avoided by making the operation idempotent instead of remembering to balance it.

The rule

When a concern has no events of its own, it borrows — and inherits the other concern's state as a side effect. Reaching for a neighbouring vocabulary is the signal that an event is missing, not that one can be shared. And the moment two owners can hold the same resource, a boolean is the wrong shape.

Exercise

One borrowing remains. PauseController.Pause() still writes application-global Time.timeScale = 0, freezing GameFlow, UI animation and every coroutine in the app — while GameTime, two files away, already scopes the freeze correctly. Find the two places in the codebase that need WaitForSecondsRealtime purely to escape it. Then decide: should a gameplay controller be able to stop the whole application's clock, and if a pause menu genuinely needs that, whose job is it?

6

Who is allowed to hear the player? Applied

JumpController.cs · Input2TempleRunAutoEventBridge.cs

Nothing here is broken at runtime. It is the most important lesson anyway, because it is about what you can still change later.

BeforeJumpController.cs
using UserInputBus = ...EventsFor<...UserInitiatedEvents>;

private void Awake()
{
    UserInputBus.Subscribe(
        UserInitiatedEvents.UserJumpRequested, OnJumpInputReceived);
}

The jump controller listens directly for a human pressing a key. Six of nine input events did this, across four controllers — even though the bridge file's own comment stated the opposite rule: "Controllers subscribe to TempleRun domain events, not UserInitiated events." Two-thirds of the code disagreed with it.

The cost is not a bug. It is that jump can now only be driven by something willing to impersonate a keyboard. A replay, a network peer, a test harness — each must publish "a user pressed jump", which is false, and each must be found and rewired in four separate controllers.

AfterInput2TempleRunAutoEventBridge.cs
{ UserInitiatedEvents.UserJumpRequested, TempleRunEvents.JumpRequested },
AfterJumpController.cs
// Subscribe to TempleRun domain events, not UserInitiated.
// This allows jump to be triggered from any source: player input, AI,
// replay, network.
TempleRunBus.Subscribe(TempleRunEvents.JumpRequested, OnJumpRequested);

One line moved the seam. All nine input events now cross in one file, and UserInitiatedEvents gained a useful asymmetry: publishing is open — input classes, AIController, any future driver — while subscribing is closed to the bridge alone. Open publishing lets an autopilot stand in for a human; closed subscribing lets the entire input layer be replaced without a controller noticing.

The rule

Ask what you would have to edit to replace a whole subsystem. If the answer is "every controller that listens to it", the seam is in the wrong place — regardless of whether anything is currently broken.
