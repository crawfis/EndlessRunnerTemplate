EndlessRunner · Architecture Review

Where the event seams leak

A review of the EndlessRunner event system, starting from one observation — that failure logic had pause logic hard-coded into it — and following that pattern through the codebase. It recurs in five distinct forms and accounted for six defects. Three are now fixed; the rest are scoped below.

The pattern, named

The original observation generalizes. Each form below is a different way a system reaches past its own boundary — and none of them are caught by the compiler, because everything compiles into Assembly-CSharp and every one of these is a legal C# expression.

Form 1

Subscribing to the cause, not the state

A consumer wants to know "the run ended" and subscribes to PlayerDied because that is how runs usually end. Any other route to the same state then silently skips it.

Form 2

Borrowing a neighbour's vocabulary

The post-failure freeze had no events of its own, so it was spelled using the pause events. Two unrelated concerns now share one state machine — and the pause events cross the bridge into GameFlow, carrying the gameplay hitch with them.

Form 3

Entering the chain at the tail

Publishing *ed directly instead of *Requested, skipping the *ing rung. The intermediate becomes unreachable, so animation and audio have no event to attach to. Found at seven sites; four remain.

Form 4

Owning what you don't own

A gameplay controller writes application-global state, or calls another controller by C# reference. The event rules don't catch it because no event is involved.

Form 5

The abandoned migration

A replacement vocabulary was declared, partly adopted, and left in place beside the original. Both survive; new code picks whichever it finds first.

Defects found

Ordered by how likely a player is to hit them. Each was confirmed by reading the code path end to end. The first three are now fixed; none of the fixes has been reproduced in Play Mode, so that verification is still outstanding.

FixedForm 1

Quit left five systems running

SegmentAdvanceTrigger, TurnCollisionDetector, DistanceController, Metronome and SetMusicPlayer all subscribed to PlayerDied — but their handlers are named OnGameEnding, OnGameOver, StopMetronome. They mean the run ended. Quitting reaches the same state without ever publishing PlayerDied:

UserQuitRequested → TempleRunEndRequested → TempleRunEnding → TempleRunEnded PlayerDied ← never published on the quit path

So on quit the music and metronome kept playing, distance kept accumulating, and turn-failure detection stayed armed. The fifth subscriber was the last one found — SetMusicPlayer.OnPlayerDied was named honestly, which is exactly why it escaped notice, though stopping the run's music is a run-ended behavior.

Fixed — all five repointed to TempleRunEnded, and the honest handler renamed OnRunEnded to match. Not an auto-chain: PlayerDied's single dictionary slot is already taken by TempleRunEndRequested.
FixedForm 2

Pressing pause during a death stumble un-paused the game

PauseController keeps an _isPaused flag set from PlayerPaused — an event it neither owns nor initiated. The failure hitch publishes that same event, so the flag is already true when the player presses pause, and the toggle resolves the wrong way:

obstacle hit → PlayerPauseRequested → … → PlayerPaused ↳ PauseController._isPaused = true player presses pause → TogglePauseResume() sees true → PlayerResumeRequested

Two independent writers shared one boolean. DeathDelay() then fired its own resume regardless, because it waits in real time.

Fixed — the failure hitch has its own lifecycle. PlayerFailing / PlayerFailed, both already in the enum and never published, now carry it; GameTime tracks freezes as a set of reasons so a hitch and a user pause can overlap without thawing each other.
FixedForm 1

The post-failure speed reset had never run

DistanceController subscribes to PlayerFailing to reset speed after a non-fatal failure. Nothing published it — publishers used only PlayerFailingAtTurn and PlayerFailingAtObstacle. Meanwhile three separate controllers each subscribed to both of those specifics to mean "failed somehow."

Fixed — both specifics now auto-chain into the generic (two keys, one value; both slots were free). One change revived the dead subscription, collapsed the duplicated pairs, and gave the failure hitch the vocabulary it needed. Watch for it in Play Mode: this behavior is switching on for the first time, so speed now genuinely resets after a non-fatal stumble.
Form 3

Power-up HUD stays lit into the game-over overlay

PowerUpBuffController.OnTempleRunEnded tears buffs down by direct call, so PowerUpDeactivating and PowerUpDeactivated never fire at run end — though every other teardown path publishes them. Any icon, VFX or SFX listening for deactivation never hears it.

Fix — publish PowerUpDeactivateRequested per active buff and let the existing chain drive teardown. Needs the PowerUpDefinition stored alongside the coroutine.
Form 5

Difficulty failures publish into the wrong family

GameDifficultyManager straddles two rival vocabularies in the same class, two fields apart: the success path publishes into the TempleRunDifficulty* set (310–318), the failure path into the bare Difficulty* set (320–323). Nothing subscribes to the latter, so difficulty-change failures are silent.

Fix — repoint to TempleRunDifficultyChangeFailed, then delete 320–323. The section comment calls them "new difficulty events (direct, non-legacy)"; the migration was declared and abandoned.
Form 1

MainMenuHidden fires twice on the level-select path

Each GameFlow panel hardcodes knowledge of every other panel: MainMenuPanelController hides on three different events, and HidePanel() publishes MainMenuHidden unconditionally. Selecting a level triggers it via LevelSelectorShowing and again via GameScenesLoading.

Fix — each panel subscribes only to its own *Hiding. The auto-chains for MainMenuHideRequested and LevelSelectorHideRequested already exist and are simply unreachable; nothing publishes their source.

Boundary violations

These don't misbehave today. They remove the replaceability the domain rule exists to protect — which is the whole reason the template is built this way.

Form 4

A player controller owns the application clock

PauseController.Pause() writes app-global Time.timeScale = 0, freezing GameFlow, UI Toolkit animation and every coroutine in the app. GameTime already subscribes to the same two events and scopes the freeze to a gameplay clock — which is what a domain-isolated pause looks like. Nothing in Assets/GameFlow or _Common writes timeScale at all.

The codebase already works around it: two separate controllers need WaitForSecondsRealtime to escape a freeze a player controller imposed.

Fix — let GameTime be the single pause-applier. If GameFlow needs the app frozen for a menu, it should do that in GameFlow, off GameFlowEvents.Paused.
Form 4

A direct cross-system method call

PlayerFailureAutoTurnController holds a serialized TurnController reference and calls ForceTurn() on it — the one place in Player/ that commands another controller by C# reference rather than through the bus. This is a literal violation of the first rule in CLAUDE.md. The failure system's decision then surfaces in the event log wearing TurnController's identity.

Fix — add TurnForceRequested (44–49 is the free range adjacent to the turning block; 57 was free when this was written but is now TurnRightStarted, and 50–59 is full) and let TurnController subscribe — it still owns ForceTurn() after the gate/commit split. Not expressible as an auto-chain: the deliberate delay before the auto-turn requires a coroutine, and auto-chains publish synchronously.
Form 4

The power-up system owns whether obstacles are lethal

PowerUpBuffController subscribes to ObstacleHit and decides the outcome for the whole game. Disable or replace power-ups and obstacles silently stop being lethal; add any non-power-up mitigation — i-frames, a forgiving difficulty, a second-chance mechanic — and you must edit the power-up manager.

Fix — a small resolver in the obstacle concern that polls registered absorbers. Restoring the bare auto-chain is not sufficient: it would fire regardless of shield, which is the validation-gate trap documented at the top of that dictionary.
FixedForm 2

Two controllers resumed a pause they never caused

PlayerLifeController published a resume purely to cancel a pause that a different controller started — so the lives system could not be swapped without knowing failure causes a pause. TeleportController resumed although nothing paused; the teleport freeze is DistanceController._isMoving, already self-contained.

Fixed — both publishes removed. The lives system no longer needs to know that failing freezes anything: the hitch now ends itself with PlayerFailed. The teleport case mattered more than it looked — with a freeze tracked per holder, a teleport ending would have released a user pause it never took.

Done

Input domain isolation

Six of nine input events bypassed the bridge and were consumed directly by gameplay controllers, contradicting the codebase's own comments. All nine now bridge; four controllers migrated; CLAUDE.md's rule rewritten around a publish/subscribe asymmetry — publishing raw input is open to any source, subscribing is closed to the bridge. UserInitiatedEvents now has zero dead members.

Done

Two inert validation gates

SlideStarting was a dead event and the slide chain never ran through it. The dash cooldown was defeated entirely — DashRequested → DashStarting auto-chained from the pre-validation event, so a dash on cooldown still fired. Three such mappings removed; each controller now publishes its own *Starting after its checks pass.

Done

The unreachable resume

GameFlowEvents.ResumeRequested had no publisher, so GameState could enter its paused state and never leave. Added the missing PlayerResumed → ResumeRequested bridge line, the counterpart to a mapping that had existed alone since the beginning.

Done

Three tail-entry publishes

PlayerFailedController, PlayerLifeController and TeleportController each published a chain's terminal state directly. The clearest evidence sat inside a single coroutine that paused by publishing the tail and resumed by publishing the head, four lines apart.

Documentation as archaeology

Twenty-eight doc-vs-code mismatches. Most are ordinary staleness, but a subset describes designs that were specified and never built — and those turned out to be the most useful findings in the whole review, because they name the missing wiring precisely.

The intended design was written down

GameFlowAutoEventFlow.cs:68 documents the chain PlayerFailing → PlayerPause … PlayerResume as though it exists. It never did — nothing has ever published PlayerFailing. The decoupling this review recommends is the design that was originally specified, recorded in a comment, and then implemented by hand inside a controller instead.

Systems named in comments that do not exist anywhere in the repository:

Named in a commentReality
GameOverControllerNo such class; GameEndRequested is referenced by nothing
LoadingScreenControllerIt is GameFlowUIPanelController
RemoteConfig updating difficultyIt is LevelConfigApplier
Sign-out / sign-in loop, leaderboard bridgesUGS events; absent from this template and not marked as removed

The Subscribes: / Publishes: contract blocks have drifted broadly — several name enum members that no longer exist (pre-User*-prefix rename), several have the direction reversed, and several omit a class's primary subscription. They are load-bearing here: they are how a reader learns what a component listens to, and how an AI agent reads the architecture.

Before deleting anything

A grep is not enough to prove an event is dead

Events are also wired through the Inspector — as serialized enum values and as [EventName] strings in scene assets. GameFlowEvents.Quitting, GameScenesUnloaded and GameScenesLoaded all look unpublished in C# and are not: they come from 0_BootStrap_Game_Only.unity, Game_Boot_0_Test_Initialization.unity and TempleRunGameplay.unity respectively.

Separately, five files still call the legacy EventsPublisher.Instance string API that CLAUDE.md describes as retired — in QuitController and four scene-management classes. They compile because the type remains in the package, and at least one path is load-bearing. Worth knowing before anyone tidies them.

Of the 61 unreferenced enum members, a large share is deliberate reserved vocabulary — the *EndRequested and *Ending rungs kept for symmetry across mechanics. The genuine cruft is narrower: the duplicate difficulty family (320–323), the entire Gameplay* family in GameFlow while Game* carries the traffic, and the Save/Load block that exists only as commented-out mappings.

Suggested order

The first two steps are done. What remains, sequenced so each makes the next smaller.

  1. Play-Mode verification. Nothing below matters until the applied fixes are exercised: quit mid-run, pause during a stumble, and confirm the speed reset — a behavior switching on for the first time.

  2. Make GameTime the only pause-applier. PauseController still writes app-global timeScale. The freeze-set is already in place, so this is now removal rather than redesign.

  3. Delete PlayerPauseController. Confirmed to appear in no scene or prefab. Not a duplicate to reconcile — dead code to remove.

  4. Give the obstacle-hit decision its own owner. The power-up system currently decides whether obstacles are lethal for the whole game.

  5. Repair the remaining contract comments. Cheap, and it is what the next reader — human or agent — will trust.
