How every tutorial wires it

public class PlayerController : MonoBehaviour
{
    public GameManager gameManager;   // dragged in the Inspector
    public ScoreUI scoreUI;             // dragged in
    public AudioSource jumpSfx;         // dragged in (reason #3 this file changed)

    void Start() => _shake = Camera.main.GetComponent<CameraShake>();  // hope it's there

    void Update()
    {
        if (!Input.GetKeyDown(KeyCode.Space) || _isJumping) return;
        _isJumping = true;
        jumpSfx.Play();
        gameManager.OnPlayerJumped();                     // …analytics lives in here?
    }

    void OnHitObstacle()
    {
        gameManager.GameOver();                           // calls back into us — careful
        FindObjectOfType<GameOverScreen>().Show(_score);  // null after a reload
    }
}

Drag it in, find it in the scene, call it. Every Unity tutorial. Honestly? Most shipped games.

Let the room recognize themselves — this is not a strawman, it's the default. Walk the smells: Inspector refs are hidden coupling (the player now *requires* a score UI to exist); Camera.main + GetComponent is a prayer about scene contents; gameManager.OnPlayerJumped() means analytics/achievements logic is reachable from the jump key; GameOver() calls back into the player — a cycle; FindObjectOfType at death time returns null after a scene reload. And every one of these concerns lives in Update() on one class.

It works. Then it rots.

  • Every feature edits an old file. Sound? Open PlayerController. Particles? PlayerController. Analytics? PlayerController. Meet the 2,000-line God file — and the team's merge-conflict magnet.
  • Delete anything, break everything. The score UI is now load-bearing for the player. Scene-load order becomes NullReference roulette.
  • Nothing runs alone. Player needs UI needs manager needs player. You can't test a piece, or open one scene by itself.
  • The wiring grows as the square. These 6 systems can hold 30 direct references; the ~30 systems of a real runner, 870 — each hand-tied, and no single place lists them.
The “why” slide for the whole talk. This isn't bad developers — it's the default gravity of GetComponent and public fields. It genuinely works at jam scale; the rot arrives with the sixth feature and the second teammate. The square-law bullet is n(n−1): 6 systems → 30 possible directed references, ~30 systems → 870 — “possible,” not actual; the point is that nothing in the direct-reference style pushes back as you approach the ceiling. Deliberately count *systems* here, not scripts: 145 small scripts is what the CLEAN codebase looks like (slide 8's punch) — spaghetti trends the other way, a few giant files with the same coupling hidden inside them. Hold the beat, then: “This template takes the opposite discipline to its logical end.”

The one rule: nobody calls anybody

A system that wants something to happen publishes a named event. Systems that care subscribe. Radio broadcast, not phone calls.

// The slide input doesn't know a slide controller exists:
UserInputBus.Publish(UserInitiatedEvents.UserSlideRequested, this, null);

// The slide controller doesn't know what asked for the slide:
TempleRunBus.Subscribe(TempleRunEvents.SlideStarting, OnSlideStarting);

Neither file mentions the other. They compile independently, load in any order, and can each be rewritten, replaced, or deleted without the other noticing.

145 scripts, and each one is coupled to exactly one thing: the bus.
This is publish/subscribe — the observer pattern — applied with zero exceptions. Contrast with the hairball: same systems, but the wiring collapses from n² possibilities to n. The two code lines are real lines from the repo. “Radio, not phone calls” is the metaphor to repeat all talk.

What a direct call quietly assumes

scoreUI.SetScore(score); — three assumptions, none of them written down:

  • “You are my only audience.” Who needs to know is hard-coded at the call site. Achievements next month? Analytics? A sound? Edit the caller. Again.
    An event names what happened — never who cares. Zero to many listeners, decided elsewhere.
  • “Your problems are my problems.” If SetScore throws, the lines after the call never run — the jump breaks because a score label was null. Failure flows backward into innocent code.
    This bus catches a throwing subscriber, logs it, and keeps delivering. The publisher never notices.
  • “You exist, right now.” Alive, initialized, findable — or NullReferenceException. Scene-load order just became your problem.
    Nobody has to be listening at all. Zero subscribers is legal — and silently doing nothing is this design's sharpest edge. We price it in Act III.
A direct call ties my success to yours. An event says: “this happened — do something with it or don't. I've got a game to run.”
Seven clicks, in two movements. Clicks 1–3 are the three red assumptions ONLY — say each in the caller's voice, it's a quote, so perform it, and let all three pile up unanswered. The gold space is already reserved, so nothing shifts. Then clicks 4–6 answer them in the same order, and 7 is the punch. Don't leak the answers early; the accumulated discomfort is what makes the rebuttal land. The “why” behind the rule, framed as the three unwritten assumptions every direct call makes. (1) Audience: a call hard-codes who needs to know; an event leaves the audience open — exactly what the jump-sound test exploits next slide. (2) Failure: in a direct call the callee's exception unwinds through the caller, so the code after the call is dead — and the opposite is verified in this bus's source: Drain() wraps every handler in its own try/catch, logs the exception, and keeps delivering to the rest; the publisher's own code never sees it. Fire-and-forget is literal here, not aspiration. (3) Existence: no null checks, no scene-order dependency; zero listeners is legal — the silent-no-subscriber risk is owned on the honesty slide (now slide 22). Nuance if asked: delivery is still synchronous and ordered — the queue fully drains before Publish returns. Decoupled failure, not deferred timing.

Anatomy of a jump

One key press, five hops, one gate — and every hop is a named, loggable event.

Walk it hop by hop. The bridge translates raw intent into the gameplay domain. The gate: JumpRequested fires whether or not the jump is legal — the controller publishes JumpStarting only after its checks pass (already airborne? cooldown?). Deliberately NOT auto-chained; programmers get the full rule in Act III. Payoff: the dashed box — a jump sound is a new subscriber to JumpStarted, zero edits to either controller. That's the open/closed principle wearing work clothes.

Three vocabularies, one door between them

  • Why domains? Different lifetimes, different owners: menus outlive runs; input outlives both. Separate enums, separate buses.
  • Why one door? The entire cross-domain surface is two bridge files, 19 mappings of data — you can read it, grep it, audit it.
Metaphor: three departments that only communicate by memo through one mailroom — and the mailroom's routing table is 19 lines. Input's arrow is one-way and asymmetric: anyone may PUBLISH raw input (keyboard, swipe, tilt, AI, replay, network) but only the bridge SUBSCRIBES — no gameplay controller is coupled to “a human pressed a key.” That asymmetry is the next slide's punchline.

Isolation is for swapping

  • 1 · Reskin without surgery. Visuals, audio, environment are separate scenes that subscribe. Swap the art; the logic never notices.
  • 2 · The player is just an input source. Keyboard, swipe, tilt, an AI, a replay file, a network peer — all publish the same requests. Only one bridge listens.
  • 3 · The menus don't know what game they're running. Level selection crosses the bridge as an integer. Swap the entire runner underneath; GameFlow doesn't change a line.

Tech

The bus: one static class per domain

using TempleRunBus = CrawfisSoftware.Events.EventsFor<CrawfisSoftware.TempleRun.TempleRunEvents>;

private void Awake()     => TempleRunBus.Subscribe(TempleRunEvents.JumpStarting, OnJump);
private void OnDestroy() => TempleRunBus.Unsubscribe(TempleRunEvents.JumpStarting, OnJump);
  • One typed enum per domain, one EventsFor<T> per enum, aliased per file
  • Static + lazily initialized: no scene GameObject, no singleton, no initialization race
  • Subscribe in Awake, unsubscribe in OnDestroy — always
War story — why static The old design: per-domain singleton components with [DefaultExecutionOrder(-10000)]. That attribute only orders Awake within one scene-load batch — additively loaded scenes made it a race anyway. Static + lazy didn't fix the race; it made the failure unrepresentable.
Why lead with this: “where does the bus live?” is the first question every Unity dev asks, and the singleton answer is a trap. The war story is real repo history — the per-domain singleton components were removed for exactly this reason. Best kind of fix: delete the category of bug.
Tech

Names are a state machine. Gates are earned.

*Requested → *Starting / *ing → *Started / *ed   (+ *Failed, *Cancelled off-ramps)

Every action in all 204 events follows this ladder. The naming convention is the lifecycle documentation.

The validation-gate rule For movement, Requested → Starting is never auto-chained. Requested is the bridge's raw translation — it fires whether or not the action is legal. The controller publishes Starting itself, after its checks pass (airborne? cooldown? lane boundary?). Auto-chain it and the gate silently dies — every illegal jump “starts.”

The #1 mistake juniors make here — and AI agents make it too. Which is why the rule lives in files machines read, not in a senior's head.

The why: the bridge cannot know gameplay legality; only the controller can. So the naming ladder has one manual rung, on purpose. Foreshadows Act V: agents and juniors fail identically, and the fix is the same — write the rule down where both will read it (CLAUDE.md, the skills, the auto-flow comments).
Tech

Control flow you can read (and audit)

// GameFlowAutoEventFlow.cs — 21 entries; TempleRun has 17 more
private static readonly (GameFlowEvents From, GameFlowEvents To)[] ChainTable =
{
    (GameFlowEvents.GameScenesLoaded,   GameFlowEvents.GameStartRequested),
    (GameFlowEvents.GameStartRequested, GameFlowEvents.GameStarting),
    (GameFlowEvents.GameEnding,         GameFlowEvents.GameScenesUnloadRequested),
};
  • Why data, not code: a domain's entire causality is one table you can read top to bottom — and audit for cycles mechanically
  • Chains fire synchronously, in declaration order; a source may fan out to several targets
War story — the dictionary ceiling The old table was a dictionary: one successor per event. Developers who found a slot taken published the second consequence by hand inside controllers — which is how failure logic came to publish pause events. The data structure's ceiling became an architecture violation. Pairs fixed the incentive.
The deep lesson: when the sanctioned path has a ceiling, people don't stop — they route around it, and the workaround is where the coupling leaks back in. Design the data structure for the behavior you want to see. (Mention: /audit-events checks the tables for cycles, since chains are synchronous.)
Tech

Payloads: typed once. Sticky: almost never.

[EventPayload(typeof(TrackSegmentInfo))]
ActiveTrackChanging = 261,        // declared on the enum member

private static readonly EventId<TrackSegmentInfo> TrackChanging
    = TempleRunBus.Id<TrackSegmentInfo>(
          TempleRunEvents.ActiveTrackChanging);

private void OnTrackChanging(string name, object sender,
                             TrackSegmentInfo segment) { }

Mint the EventId<T> once; everything downstream is compiler-checked. Two call sites disagreeing on T? Reported at startup.

State, not moments. Default delivery is transient. Sticky (replayed to late subscribers) is only for an event that states something still true — “the selected level is 3.” Replaying a moment (“menu hiding”) to a latecomer is actively wrong.

The trap: Paused/Resumed each mark a moment, not the state — sticky can't fix that; a late subscriber gets whichever fired last. Carry the current state in one value-carrying event.

Discipline stat: 2 sticky of 204.
And upgrades are measured, not vibed: an in-editor audit reports which events actually had late subscribers after a play session.

Why late subscribers exist at all: additive scenes load at different times, so “who heard what” is a real problem. The two sticky events are TempleRunLevelApplied and TempleRunDifficultySettingsApplied — both statements of current state that stay true, read at init via TryGetLast. The measurement tool is Window ▸ Events ▸ Upgrade Audit: evidence, then upgrade.
