        jumpSfx.Play();

Every direct call makes three promises

scoreUI.SetScore(score); — none of them written down:

  • “You're my only audience.” Who needs to know is hard-coded at the call site.
    An event names what happened, never who cares. Zero to many listeners, decided elsewhere.
  • “Your crash is my crash.” If SetScore throws, the lines after the call never run. The jump breaks because a label was null.
    This bus catches a throwing listener, logs it, keeps delivering. The publisher never notices.
  • “You exist, right now.” Alive, initialized, findable — or NullReferenceException.
    Nobody has to be listening at all. Zero subscribers is legal — and that's this design's sharpest edge. We price it in Act III.
A call ties my success to yours. An event says: “this happened. Do what you like with it.”
SAY: three clicks. Click 1 puts all three red promises up at once — say each in the CALLER'S voice, they're quotes, so perform them. Let the discomfort accumulate. Click 2 answers all three in the same order. Click 3 is the punch. The gold space is pre-reserved, so nothing shifts on screen when the answers land. DETAIL if a programmer asks about #2: verified in the package source — Drain() wraps every handler in its own try/catch, logs, and continues to the rest. Fire-and-forget is literal here, not aspirational. Nuance: delivery is still synchronous and ordered — the queue fully drains before Publish returns. Decoupled failure, not deferred timing. public class AIController : MonoBehaviour        // the whole file, lightly trimmed
{
    [SerializeField] private TurnController _turnController;   // same domain — legal to read
    [SerializeField] private float _turnDistance = .1f;
    [SerializeField] private bool  _isEnabled    = true;       // ← the checkbox you ticked

    private void Update()
    {
        float distance = Blackboard.Instance.DistanceTracker.DistanceTravelled;
        if (!_gameStarted || !_isEnabled ||
            _turnController.TurnFailedDistance - _turnDistance > distance) return;

        UserInputBus.Publish(_turnController.TurnDirection == Direction.Left
            ? UserInitiatedEvents.UserLeftTurnRequested
            : UserInitiatedEvents.UserRightTurnRequested, this, distance);
    }
}
Publishes the same two events the arrow keys do. Reads the turn window off TurnController — same domain, legal, and exactly why it's a perfect turner.

Tech

The bus: one static class per domain

using TempleRunBus = CrawfisSoftware.Events.EventsFor<CrawfisSoftware.TempleRun.TempleRunEvents>;

private void Awake()     => TempleRunBus.Subscribe(TempleRunEvents.JumpStarting, OnJump);
private void OnDestroy() => TempleRunBus.Unsubscribe(TempleRunEvents.JumpStarting, OnJump);
  • One enum per domain, one EventsFor<T> per enum, aliased per file
  • Static and lazily initialized: no scene object, no singleton, no init race
  • Subscribe in Awake, unsubscribe in OnDestroy — always
War story — why static The old design used per-domain singleton components with [DefaultExecutionOrder(-10000)]. That attribute only orders Awake within one scene-load batch — and our scenes load additively, so it was a race anyway. Static + lazy didn't fix the race. It made the failure unrepresentable.
WHY LEAD WITH THIS: “where does the bus live?” is the first question every Unity developer asks, and the singleton answer is a trap that costs a week. The war story is real repo history — those per-domain singleton components were deleted for exactly this reason. The lesson to state out loud: the best kind of fix deletes the category of bug, rather than handling it.
Tech

Names are a state machine. Gates are earned.

*Requested → *Starting → *Started   (+ *Failed, *Cancelled off-ramps)

Every action in all 204 events climbs this ladder. The naming convention is the lifecycle documentation.

The validation-gate rule For movement, Requested → Starting is never automatic. Requested is the bridge's raw translation — it fires whether or not the action is legal. The controller publishes Starting itself, after its checks pass. Automate that hop and the gate dies silently: every illegal jump “starts.”

The #1 mistake juniors make here — and AI agents make it too. Which is why the rule lives in a file machines read, not in a senior's head.

THE WHY: the bridge cannot know gameplay legality; only the controller can. So the ladder has exactly one manual rung, on purpose. This slide foreshadows Act IV directly: agents and juniors fail identically here, and the fix is identical — write the rule down where both will read it (CLAUDE.md, the skills, the comments in the auto-flow file). If a programmer asks “why not just validate in the bridge?” — because then the bridge knows about cooldowns, airborne state and lane boundaries, and you have re-created the coupling you deleted.

Control flow you can read (and audit)

// GameFlowAutoEventFlow.cs — 21 entries; TempleRun has 17 more
private static readonly (GameFlowEvents From, GameFlowEvents To)[] ChainTable =
{
    (GameFlowEvents.GameScenesLoaded,   GameFlowEvents.GameStartRequested),
    (GameFlowEvents.GameStartRequested, GameFlowEvents.GameStarting),
    (GameFlowEvents.GameEnding,         GameFlowEvents.GameScenesUnloadRequested),
};
  • Why data, not code: a domain's entire causality is one table you read top to bottom
  • Chains fire synchronously, in declaration order. One source may fan out to several targets.
War story — the dictionary ceiling This used to be a dictionary: one successor per event. Developers who found a slot taken published the second consequence by hand, inside a controller — which is how failure logic came to publish pause events. The data structure's ceiling became an architecture violation. Pairs fixed the incentive.
THE DEEP LESSON, and the best line in Act III: when the sanctioned path has a ceiling, people don't stop — they route around it, and the workaround is exactly where the coupling leaks back in. Design the data structure for the behavior you want to see. Mention that /audit-events checks these tables for cycles, since chains fire synchronously — a cycle is an infinite loop, not a slow frame.
Tech

State, not moments

[EventPayload(typeof(TrackSegmentInfo))]
ActiveTrackChanging = 261,     // declared on the member

private static readonly EventId<TrackSegmentInfo> TrackChanging
    = TempleRunBus.Id<TrackSegmentInfo>(
          TempleRunEvents.ActiveTrackChanging);

Mint the id once; everything downstream is compiler-checked. Two call sites disagreeing on T are reported at startup.

Replay a state, never a moment. Default delivery is transient. Sticky — replayed to late subscribers — is only for something still true: “the selected level is 3.”

The trap: Paused / Resumed are two moments, not a state. Sticky can't fix that — a latecomer gets whichever fired last. Carry the state in one value-carrying event.

Discipline stat: 2 sticky out of 204.

And upgrades are measured, not vibed — an in-editor audit reports which events actually had a late subscriber after a play session.
WHY LATE SUBSCRIBERS EXIST AT ALL: additive scenes load at different times, so “who heard what” is a real, structural problem — not sloppiness. The two sticky events are TempleRunLevelApplied and TempleRunDifficultySettingsApplied. Both are statements of current state that stay true; TrackManager reads the level at init with TryGetLast rather than subscribing. The measurement tool is Window ▸ Events ▸ Upgrade Audit. The rule: evidence first, then upgrade. A name is not evidence.

Q&A cheat sheet

If they ask…Say
Why an enum bus, not C# events / UnityEvents / SO-events?Events-as-data is what buys the tooling: the logger, the flight recorder, the chain tables, the generated catalog, the upgrade audit. You can't enumerate or diff event Action.
Isn't this over-engineering for a runner?The direct version works at small scale, then rots. And the swaps answer it: the AI driver, the artist tasks and the cloud sibling all shipped through seams nobody had to add later.
Performance of all that indirection?Events fire on state transitions, not per frame — the hottest is the distance tick. Dispatch is synchronous, no reflection at publish. It has not been a bottleneck; profile before believing anyone, including me.
Why no assembly definitions?Deliberate simplicity for a student codebase — one assembly, fast onboarding. The trade is owned on the honesty slide: review and /audit-events are the enforcement.
Does the AI break the architecture?Yes, the same ways juniors do — headline case, automating past a validation gate. That's why the rules live in files the agent must read and why the audit runs before merge.
